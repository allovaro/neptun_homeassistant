# Интеграция для системы защиты от протечек Neptun ProW+Wifi
![Neptun module](https://user-images.githubusercontent.com/6770608/131808089-1a143063-1377-4b84-9ddc-fa2b91065511.png)
## Возможности
Интеграция для системы [Home Assistant](https://www.home-assistant.io/ "Home Assistant") позволяет получать:
- *сигналы от проводных датчиков*
- *сигнал о протечке*
- *данные счетчиков воды (если используются)*
- *режим уборки (вкл/выкл)*
- *состояние кранов (открыто/закрыто)*

Для управления доступны:
- *Краны*
- *Режим уборки*
## Подключение
Просто чтоб не потерять

![Схема подключения](https://user-images.githubusercontent.com/6770608/131808117-5afb8971-9685-4976-bc93-2a297bd94901.jpg "Схема подключения")
## Описание
Интеграция мимикрирует под приложение для Android. Работает только по локальной сети без выхода в интернет. API [SST Cloud](https://api.sst-cloud.com/docs/ "SST Cloud") не используется.

## Настройка Home Assistant
1. Скопировать папку *custom_components/neptun* в конфиг
2. Добавить в `configuration.yaml`:

```yaml
neptun:
  host: 192.168.1.100
```

Всё остальное определяется автоматически: количество проводных линий, какие слоты
счётчиков реально настроены и сколько беспроводных датчиков привязано. Отдельные
блоки `binary_sensor:`, `sensor:` и `switch:` больше не нужны — их можно удалить.

### Необязательные параметры

| Параметр | По умолчанию | Зачем |
| --- | --- | --- |
| `port` | `6350` | Порт контроллера |
| `scan_interval` | `30` | Период опроса |
| `timeout` | `5` | Таймаут одного обмена, секунды |
| `retries` | `4` | Попыток за один опрос, разнесены по времени, см. ниже |
| `failure_tolerance` | `3` | Сколько опросов подряд можно провалить, удерживая последнее показание, прежде чем уводить сущности в `unavailable` |
| `counters` | авто | Сколько счётчиков показывать (`0`–`4`), если автоопределение не устраивает |
| `lines` | авто | Сколько проводных линий показывать |
| `wireless_record_size` | `4` | Размер записи беспроводного датчика, см. ниже |

### Создаваемые сущности

```
binary_sensor.neptun_sensor_N     проводная линия N (device_class: moisture)
binary_sensor.neptun_valves       положение кранов
binary_sensor.neptun_dry          режим уборки
binary_sensor.neptun_alarm        авария (device_class: safety)
binary_sensor.neptun_wireless_N   беспроводной датчик N
sensor.neptun_counter_N           счётчик N, м³ (device_class: water)
switch.neptun_valves              управление кранами
switch.neptun_dry                 управление режимом уборки
```

### Счетчики
Можно добавить сенсоры для вывода месячных и ежедневных показаний силами Home Assistant например так:
```yaml
utility_meter:
  cold_water_daily:
    source: sensor.neptun_counter_1
    cycle: daily

  warm_water_daily:
    source: sensor.neptun_counter_2
    cycle: daily

  cold_water_monthly:
    source: sensor.neptun_counter_1
    cycle: monthly

  warm_water_monthly:
    source: sensor.neptun_counter_2
    cycle: monthly
```

## Протокол
Разобран по обмену с контроллером N3220. Кадр в обе стороны:

```
02 'T' <dir> <op> <длина:u16be> <payload> <crc:u16be>
```

`dir` — `Q` для запроса, `A` для ответа; `op` — `R` чтение, `W` запись. `длина`
описывает только payload. Контрольная сумма — **CRC-16/CCITT-FALSE** (полином
`0x1021`, начальное значение `0xFFFF`, без реверса и финального xor) по всем
предшествующим байтам кадра.

Payload — последовательность TLV-блоков `<тег:1> <длина:u16be> <значение>`:

| Тег | Содержимое |
| --- | --- |
| `I` | модель, например `N3220` |
| `M` | MAC-адрес строкой |
| `A` | 1 байт, назначение неизвестно |
| `S` | статус: `[краны, ?, ?, уборка, ?, ?, авария]` |
| `s` | беспроводные датчики, пусто пока ни один не привязан |
| `L` | проводные линии, по байту на линию |
| `C` | счётчики, по 5 байт: `u32be` литров + шаг импульса |
| `D` | часы контроллера, unix-время строкой |
| `W` | 1 байт, назначение неизвестно |

Полезные следствия:

- **Число счётчиков видно из данных.** У ненастроенного слота шаг равен нулю,
  поэтому пустой слот отличается от счётчика, который честно показывает `0`.
- **Число линий — это длина блока `L`.**
- **Беспроводные датчики живут в блоке `s`.** Разбивка блока на записи пока
  сделана по 4 байта (`[авария, батарея, сигнал, резерв]`) и на живых датчиках
  не проверялась — их не было под рукой. При первом непустом блоке интеграция
  пишет его hex в лог: этого дампа достаточно, чтобы доделать разбор. Размер
  записи меняется параметром `wireless_record_size`.

### Одна сессия за раз
Контроллер обслуживает **одно** соединение. Лишние подключения он принимает, но
не отвечает на них до таймаута. Замер на N3220:

| Как опрашиваем | Успешных ответов |
| --- | --- |
| последовательно | 8 / 8 |
| 2 соединения одновременно | 1 / 2 |
| 4 соединения одновременно | 2 / 4 |
| 9 соединений одновременно | 4 / 9 |

Отсюда прежний совет «опрашивать не чаще раза в 5 секунд»: дело было не столько
в частоте, сколько в том, что каждая сущность ходила к контроллеру своим
соединением. Теперь опрос общий на всю интеграцию и сериализован, так что
`scan_interval: 30` — это одно подключение раз в 30 секунд.

### Провалы связи
Даже при одном опрашивающем контроллер периодически замолкает — принимает
соединение и не отвечает либо сразу закрывает сокет, продолжая при этом
отвечать на ping. Замер: 22 минуты опроса каждые 3 секунды дали 237 удачных из
280. Почти все провалы одиночные, короче ~6 секунд, но однажды контроллер
молчал ~50 секунд подряд.

Две меры на два случая:

- **Разнесённые ретраи** гасят частые короткие провалы. Попытки одного опроса
  раскиданы по времени (при `timeout: 5` и `retries: 4` опрос длится ~26 секунд),
  так что окно в ~10 секунд не может накрыть их все — хоть одна попадёт в
  просвет, и сущность даже не мигает.
- **`failure_tolerance`** переживает редкий затяжной провал: сущности держат
  последнее показание несколько опросов подряд и уходят в `unavailable`, только
  если контроллер молчит уже по-настоящему долго. Это безопасно — реакцией на
  протечку заведует сам контроллер (закрывает краны без участия Home Assistant),
  так что кратковременно устаревшее показание на физику не влияет.

## Разработка без железа
`test_server.py` — контроллер-заглушка. Он считает настоящую CRC и применяет
команды записи, а не проигрывает один записанный буфер:

```bash
./test_server.py                        # исправный блок: 4 линии, 2 счётчика
./test_server.py --counters 4 --leak 3  # все счётчики настроены, линия 3 мокрая
./test_server.py --truncate             # отдать половину кадра
./test_server.py --corrupt              # отдать кадр с битой CRC
./test_server.py --hang 2               # промолчать на первые 2 запроса
./test_server.py --single-session       # не отвечать на параллельные сессии
```

`test_client.py` прогоняет клиент по всем этим сценариям, железо не нужно:

```bash
./test_client.py
```

## Что изменилось в 0.2.0
- **Кадр дочитывается целиком.** Раньше был один `recv(100)`, который возвращает
  столько, сколько успело прийти. На обрезанном кадре счётчики падали с
  `ValueError`, а датчики протечки молча читались как «сухо» — для системы защиты
  от протечек это была самая неприятная из ошибок.
- **Проверяется CRC** каждого ответа.
- **Ретраи вместо мгновенного «устройство пропало».** Одиночный сбой больше не
  переводит все сущности в `unavailable`.
- **Общий опрос через `DataUpdateCoordinator`** и блокировка: одно соединение за
  раз вместо девяти конкурирующих.
- **Починено управление.** Команды теперь собираются, а не берутся из готовых
  строк, поэтому доступна и комбинация «краны закрыты + режим уборки», которую
  прежний код отправить не мог. Раньше включение режима уборки заодно открывало
  краны, а `set_state()` всегда возвращала `False` из-за кириллической буквы `с`
  в константе подтверждения.
- **Состав сущностей определяется по данным контроллера**, а не задаётся руками
  в `monitored_variables`.
